# Project Overview: ChatBlue

## Project Description
ChatBlue is a Flutter-based peer-to-peer chat application supporting **three transports**: Bluetooth Classic (RFCOMM), Wi‑Fi Direct (P2P over framed TCP sockets), and Google Nearby Connections (BYTES payloads carrying the same framed stream). All transports are implemented natively in Kotlin and exposed via Platform Channels. State management runs entirely on Riverpod — app state (locale, theme, session list, transports) and the chat controllers (GetX was removed completely: MaterialApp host, gen-l10n as the single translation source); chat sessions, messages and app settings are persisted locally with drift (SQLite) — Hive (CE) was removed after a device-verified migration — including image message transfer with progress tracking. The UI follows a modern navy/cyan design language with full light/dark theming. Outgoing bubbles carry **delivery ticks** (sent → delivered) confirmed by a peer `ack` frame, and every chat's Connect button offers a **three-way transport picker** (Bluetooth / Wi‑Fi Direct / Nearby). Chat history loads lazily: a chat opens on the newest **20** messages and pages **+5** older messages per step as the user scrolls toward the edge of the loaded window (paged reads + windowed saves — the unloaded history stays intact in the store). Message history is grouped by calendar day: every day older than today carries a day separator pill, and a pinned chip at the top of the list follows the day currently at the top of the view. The home list shows each chat's **last message** as its subtitle (with the activity time) and a long-press action sheet offers a per-chat **nickname** — a user-chosen title that overrides the auto-tracked device name everywhere the session title renders (and, when cleared, falls back to the current device name).

## Architecture
- **Framework**: Flutter
- **State Management**: Riverpod 3 for all state (locale, theme, session list, transports, chat — notifiers + immutable state); chat screens run on `chatControllerProvider` (`lib/providers/chat_controller.dart`), the transport surface via `lib/controllers/chat_transport_binding.dart`
- **Local Storage**: drift (SQLite) with codegen (`drift_dev`) — chat sessions + messages + app settings (theme mode, locale, device id) in `chatblue.sqlite`; legacy Hive (CE) boxes remain on old devices as inert files (data was carried over by one-time importers during the migration)
- **Bluetooth (Classic)**: Custom Android native implementation via Platform Channels
- **Wi‑Fi Direct (P2P)**: Custom Android native implementation via Platform Channels
- **Platform Channels**:
  - Bluetooth
    - MethodChannel: `com.sondermium.chatblue/bt` (isBluetoothAvailable, isBluetoothEnabled, requestEnableBluetooth, requestBluetoothPermissions, requestDiscoverable, startScan, stopScan, getDiscoveredDevices, clearDiscoveredDevices, getPairedDevices, startServer, stopServer, connect, disconnect, isConnected, getLiveRssi, sendString, sendBytes)
    - EventChannels: `com.sondermium.chatblue/scan` (started/device/finished), `com.sondermium.chatblue/socket` (connected/disconnected/data/progress)
  - Wi‑Fi Direct
    - MethodChannel: `com.sondermium.chatblue/wd` (isWifiP2pSupported, requestWifiDirectPermissions, isWifiEnabled, requestEnableWifi, isLocationEnabled, requestEnableLocation, getThisDeviceAddress, getDeviceName, startDiscovery, stopDiscovery, getDiscoveredPeers, requestPeers, clearDiscoveredPeers, createGroup, removeGroup, connect, disconnect, isConnected, getLiveRssi, sendString, sendBytes)
    - EventChannels: `com.sondermium.chatblue/wd_scan` (started/peer/finished), `com.sondermium.chatblue/wd_socket` (connected/disconnected/data/progress)
  - Nearby Connections
    - MethodChannel: `com.sondermium.chatblue/nearby` (getNearbyStatus, getDeviceName, requestNearbyPermissions, requestEnableLocation, openAppSettings, requestEnableBluetooth, startScan, stopScan, connect, cancelConnect, accept, reject, disconnect, isConnected, sendString, sendBytes)

  - App utility
    - MethodChannel: `com.sondermium.chatblue/util` (openFile — FileProvider viewer/installer flow for received files and APKs; openMap — `geo:` intent with an https fallback)
- **Data Models**: `ChatSessionModel` and `MessageModel` (plain data classes since the drift migration) in `lib/core/models` — sessions carry a persisted `transport` tag (`'bt'`/`'wfd'`/`'nearby'`; null on old records) and an optional user `nickname` (display-only user title; `title` resolves nickname → device name, `lastMessage` is the home subtitle preview)
- **Services**:
  - `SessionRepository` — drift CRUD for sessions/messages (`lib/data/session_repository.dart`); `watchSessions()` feeds the home list (rows carry their messages, so the last-message subtitle needs no extra query); paged message reads (newest-first window + keyset cursor) and windowed upserts (regular saves never delete — removals are explicit); `setSessionNickname()` sets/clears the user title without touching the device name or `updatedAt`; `SettingsRepository` — drift key/value store with a startup cache (`lib/data/settings_repository.dart`; theme mode/locale/device id)
  - `themeModeProvider` / `localeProvider` — persistent theme mode + app language (en/tr) in the drift settings store as Riverpod notifiers (`lib/providers/app_providers.dart`); first launch follows the device language (TR device → Turkish, else English)
  - `BtClassicService` — Bluetooth ops with typed event streams + callbacks (`lib/core/services/bt_classic_service.dart`) over `BtPlatformChannel`
  - `WifiDirectService` — Wi‑Fi Direct ops, same pattern (`lib/core/services/wd_service.dart`) over `WdPlatformChannel`
  - `NearbyService` — Nearby Connections ops, same pattern (`lib/core/services/nearby_service.dart`) over `NearbyPlatformChannel` (advertise+discover, connection accept lifecycle, typed scan/socket streams)
- **Theming**: `AppTheme` (light/dark, cyan seed, navy canvas) in `lib/core/theme/app_theme.dart`; chat screens use a theme-aware `ChatPalette` (dark = navy glass, light = bright variant)
- **Controllers**:
  - `BtTransportNotifier` / `WdTransportNotifier` — Riverpod ports of the former GetX transport controllers (scan/socket lifecycle, two-stage handshake, connect + awaiting-acceptance, WFD discovery-based reconnect; immutable state; their user-facing strings resolve through `transportKeyToL10n` against the current `AppLocalizations`) in `lib/providers/transport_providers.dart`; exposed app-wide via `btTransportProvider`/`wdTransportProvider`
  - `NearbyTransportNotifier` — Nearby Connections transport (`lib/providers/nearby_transport_providers.dart`): advertise+discover scanning, incoming-request banner keyed off the native `incoming` flag (our own dial can never show a banner), two-window connect flow, uid-then-name session reconnect with the shared device picker, Play Services/Bluetooth precondition gates; exposed via `nearbyTransportProvider`
  - `ChatTransportBinding` / `chatBindingProvider` — the transport surface the chat controller consumes (`lib/controllers/chat_transport_binding.dart`): typed listener fan-out over the Bt/Wd transport notifiers (connection / disconnect-reason / peer-name), method delegation (`connectToPeer`, `connectToSessionPeer`, `sendMessage`/`sendBytes`, `disconnectFromDevice`, `dialSettled`/`cancelPendingConnect`), `onChatOpened()`/`onChatClosed()` lifecycle
  - `homeSessionsProvider` — chat session list (live drift `watchSessions()` stream + delete + `setSessionNickname`, replacing HomeController's load/refresh flows) (`lib/providers/home_providers.dart`)
  - `ChatController` / `chatControllerProvider` — single implementation of the conversation logic (messages, image/voice transfers, persistence, history sync, send queue) for all three transports (`lib/providers/chat_controller.dart`); Riverpod `Notifier` family + autoDispose over `ChatOpenArg` (one instance per chat open); stamps the `transport` tag on sessions; history sync re-arms on every disconnect (per-connection)
- **Screens**:
  - `HomeScreen` — session list + bottom navigation (Chats / Bluetooth / Wi‑Fi / Nearby tabs); each row shows the chat title (the user nickname when set), the **last message** as its subtitle and a transport badge (Bluetooth / Wi‑Fi Direct / Nearby), and opens the chat on its own transport; a long-press opens the action sheet — **Set nickname** (the rename dialog; empty save clears it) and Delete (the previous long-press flow)
  - `SettingsScreen` — theme switching (System/Light/Dark) + app info + the **Storage** section (Clear cache: deletes local media copies into re-downloadable placeholders, sweeps orphans/temp, reports freed space) (`lib/screens/settings/settings_screen.dart`)

  - `WifiDirectScanScreen` — WFD discovery/server (group) mode/connect
  - `NearbyScanScreen` — Nearby advertise+discover/endpoint list/connect (Play Services + Bluetooth + location-permission + location-off panels, Wi‑Fi-off info note, mount/resume status refresh; no server mode; `canAdvertise` capability note)
  - `BChatScreen` / `WChatScreen` / `NChatScreen` — per-transport conversation UI built from the shared `chat_ui` kit (ChatAppBar — carries the quality-panel toggle, ChatLinkPanel, ChatMessageList, ChatMessageBubble, ChatInputBar, ChatSyncBanner, Connect bar, image preview); `ConsumerStatefulWidget` — the chat's `ChatOpenArg` is built once in `didChangeDependencies` and closed in `dispose`

## Notable Implementation Details
- Android Bluetooth Classic (`BluetoothClassicManager`): discovery with RSSI, bonded devices, discoverable request, RFCOMM SPP server/client (accept + connect threads), framed byte-stream protocol, string/byte transfer with progress callbacks, known-address persistence via SharedPreferences. The accept loop stays alive after a connection (peers can reconnect to an already-started server; a new peer replaces the current socket with "replaced").
- Android Wi‑Fi Direct (`WifiDirectManager`): peer discovery, group creation/removal (GO negotiation), client connection via WifiP2pInfo, TCP server/client socket threads with the same framed protocol and progress events; server thread also keeps accepting (same reconnect semantics); permission feature checks.
- Framed protocol: message frames carry a type flag ('text' vs 'bytes') and a 4-byte length; both managers emit `onTransferProgress(direction, current, total, kind)` and `onSocketData(bytes, text, kind)` on separate reader threads; writes run on a single-thread executor (atomic frames, FIFO order).
- `SessionRepository` persists sessions/messages in drift (sessions keyed by id, sorted by `updatedAt`; full-state writes in one transaction); `MessageModel` stores `imagePath` (not in-memory bytes) plus optional transfer state fields.
- **History sync** (`ChatController`, SHA-256 based): on (re)connection each side sends a tiny **manifest** — digests of its last 10 messages (text: `sha256(text)`, images/voice: `sha256(file bytes)` + occurrence count). The peer compares against its local set and **requests only what it actually misses**; requested messages travel as `message` packets, each media file in its own packet (base64, ≤ 3 MB). When both sides match, no payload is transferred at all. Dedup uses (text + direction + ±10 s) with the SHA content-hash as fallback. Sync runs once per chat screen, outside the user send queue; a thin "Syncing history…" banner shows frame progress.
- **Send queue**: user text/image sends are serialized in a FIFO queue — an in-flight image transfer never interleaves with other sends; bubbles appear immediately, writes are ordered.
- Image messages: outgoing images are compressed pre-send **and the message stores exactly the bytes that go on the wire** (compress once, persist that copy — byte-identical replicas keep the content-hash dedup and the sync manifest hashes matching across devices; a divergent stored copy used to bring duplicate bubbles back after a sync); both directions use progress bubbles that finalize to image bubbles once transfer completes; incoming bytes saved under application documents directory (background isolate).
- Chat UX: connection status in the header (glowing dot), composer hidden when disconnected and replaced by a **Connect** button that reconnects to the session's device — Bluetooth dials the stored MAC; Wi‑Fi Direct runs peer discovery and connects on an address/name match (`connectToSessionPeer`), surfacing the native failure reason (`lastConnectError`) when nothing is found; clearing conversation and full-screen image preview with save-to-gallery (Android 13+ `Permission.photos`/`READ_MEDIA_IMAGES`, older `Permission.storage`; iOS `photosAddOnly`/`photos`).
- **Voice messages**: tap-to-record (mic button in the composer, runtime `RECORD_AUDIO`), live "Recording 0:12 · Cancel" banner, automatic cut-off & send at 120 s. Files are AAC-LC (.m4a) written to app documents; a short announcement frame (`@@CHATBLUE_AUDIO@@{"duration":…}`) precedes the bytes; transfers reuse the image byte channel (progress bubbles). Voice bubbles offer play/pause, a draggable seek slider and ±10 s jumps (single `just_audio` player); messages persist as `transferKind: 'audio'` + file path (no new model fields) and sync as `type: "audio"` packets.
- **Connection-quality panel** (`ChatLinkPanel`, on all three chat screens): hidden by default — the chat app bar's signal icon toggles it and persists the choice per device (`connectionPanelVisible`). Rows: link state + connected-for uptime, live traffic (session totals + a 5-second-window rate via `LinkStats`), and the signal line. Signal readings are honestly labelled: the dialer shows its scan-time RSSI `(last scan)` — and a dial WITHOUT scan context (the chat's Connect button / transport picker) reuses the last reading ever seen for that device (in-memory from scans, persisted as `btRssi:<MAC>` in the settings store so a restart keeps it; Classic has no live RSSI, so a scan value is the only source that can exist); the accepting side — which never scanned — receives the peer's reading pushed over a `linkShare` sync frame `(peer reading)` (one retry; older builds drop unknown sync types via their `default:` branch, so mixed versions stay safe). There is NO live RSSI for a connected Bluetooth Classic link (the hidden `BluetoothDevice.getRssi()` does not exist in AOSP — verified against the 10/11/12 sources plus the modern Bluetooth module; the old reflection probe was removed); Wi‑Fi Direct keeps a genuine client-side live read (`WifiManager.connectionInfo`) and none on the GO side — the client pushes that live value over `linkShare` at (re)connect and re-shares it while connected on a 5 s change-guarded cadence (≥ 2 dBm), so the GO side's `(peer reading)` tracks the real link instead of showing nothing. The panel rides flush under the app bar (top corners square). Nearby Connections has no RSSI anywhere in its API (verified against the 19.5.1 AAR): its one official metric — GMS bandwidth quality (`ConnectionLifecycleCallback.onBandwidthChanged` → `BandwidthInfo.getQuality()`) — renders on Nearby chats as a `Link quality: <Low|Medium|High|Unknown>` line (the BT/WFD binding returns null, so the line exists on Nearby only; the panel's 1 s ticker repaints it).
- **File sharing**: an announcement frame (`@@CHATBLUE_FILE@@{"name":…,"size":…}`) precedes the bytes (the voice-message pattern; progress bubbles reuse the existing byte channel), 20 MB outbound cap, blocked when the peer's protocol version is pre-file (`pv < 2`). Received files land under `documents/received/` with the sanitized original name (timestamp prefix on collision) and open via the new `util` platform channel (FileProvider shares `cache/open/`); the bubble shows the name + size. APKs go through the install flow: `REQUEST_INSTALL_PACKAGES` plus a `canRequestPackageInstalls()` gate — without the per-app grant the tap opens the matching settings page with an explanatory notice (a chooser-wrapped install intent is silently swallowed on MIUI/HyperOS), with the grant the explicit installer intent fires directly.
- **Location sharing**: a one-shot fix encoded as plain, language-agnostic text (`📍 41.008237, 28.978358 ±12m` + a maps link) so any build renders it readably; the local build shows the rich bubble and opens the coordinates through the `util` channel (`geo:` intent, https fallback).
- **BT scan list (J7 fix)**: every discovered device is listed the moment the inquiry reports it — the per-device `fetchUuidsWithSdp` probe with its app-UUID gate is gone (SDP cannot complete during an ongoing inquiry, which left old-stack lists permanently empty; on Marshmallow+ an unbonded probe can also trigger pairing prompts), and devices that never broadcast a name are filtered in the transport notifier, with the inquiry's own `EXTRA_NAME` as the name fallback on old stacks.
- **Delivery ticks**: outgoing bubbles render ⏱ (queued) → ✓ (socket write done) → ✓✓ (peer confirmed storage), with a red alert on a failed write; incoming bubbles show none; legacy rows (no state) fall back to a single tick. The state persists per message (`messages.delivery`). The receiver confirms stored peer messages with batched `ack` sync frames (`{"type":"ack","items":[fingerprints]}`, ~400 ms batch window, cleared on disconnect); fingerprints are content-based — `d:t:<sha256(text)>` / `d:m:<sha256(exact stored bytes)>` (the stored-media byte-identity invariant keeps both ends identical). The sender matches text first, then media through a lazy per-message file-hash cache (scan capped at the 20 newest undelivered); duplicates re-ack on every encounter, so a re-serve after a lost ack still flips the tick. Deliberately NO manifest-based delivery guessing (content collisions would false-flip double ticks). Mixed versions: older builds drop the unknown `ack` type via their `default:` branch — single tick only (honest "sent").
- **Transport picker (chat Connect button)**: `showTransportPicker` (chat_ui) renders the three channels with their icons, accent medallions and hints; `ChatController.connectViaTransport` delegates same-kind to the classic reconnect and cross-kind to that transport's session-reconnect flow behind the existing cancellable connecting panel (`dialTransportPeer`; `ChatTransportBinding` gained `dialSettled`/`cancelPendingConnect` delegates), then reports the outcome from the target transport's live state (declined notices stay single-surface). On success the target transport pushes its own chat screen and the session reconciliation merges both channels into one conversation. Bluetooth's cross-kind dial uses the stored MAC (a session that never had a BT link fails fast with the localized invalid-address message).
- **Text-bubble actions** (`showMessageActionsDialog`): long-press on a text bubble opens a themed dialog (Copy in both directions, Delete for own finished messages). `SelectableText`'s selection toolbar is deliberately not used — its follower-layer machinery trips a layout assertion in this Flutter version (`RenderFollowerLayer` vs the OverlayPortal deferred layout) and its copy action took the whole message anyway.
- Dialog/snackbar hygiene: loading dialogs are closed via the root navigator (by their own `DialogRoute` reference — never a blind `pop()` while a snackbar or the freshly pushed chat route is up); socket errors are logged only (no snackbar spam); scan errors still surface.
- Progress bubbles are tracked by message id (bubble UUID); session writes are debounced (250 ms) and flushed on close; outgoing images are compressed exactly once.
- **Paged history (message window)**: a chat's `state.messages` holds the visible window only — the newest `initialMessageWindow` (20) on open (a seeded home open slices its stored list; a transport open reads 21 rows via `loadRecentMessages` so the extra row tells whether older history exists) and `olderPageSize` (5) more per `loadOlderMessages()` call, appended at the OLDEST end (the reverse list keeps its scroll position). Older pages fetch through a keyset cursor (`loadMessagesBefore`, strictly-older `(timestamp, id)` pair — matching the read order `timestamp DESC, id DESC`, so pages can neither skip nor repeat rows; `seq` is write-only legacy and a `(session_id, timestamp)` index backs the reads). Regular saves are windowed upserts (`saveChatSessionWindow` — no deletes); removals are explicit (`deleteMessageRow`/`clearSessionMessages`); the peer-merge absorb loads both COMPLETE histories before its full rewrite. `ChatState.hasMoreOlder` drives the pre-fetch trigger in `ChatMessageList` — within `olderPrefetchBuffer` (5) messages of the oldest loaded one, i.e. the 15th message of the initial window. The history sync dedups re-served messages against the STORE (`hasMessageNear`, text+direction+±10 s) since a duplicate may sit below the loaded window.
- **Day separators & pinned day chip** (message list): the list builds ENTRIES — bubbles plus one separator pill per calendar day older than today (`"Dün"`/`"Yesterday"`, else `DateFormat.yMMMMd` of the app locale via `intl`); today's rows stay unlabelled (labels surface beyond the last 24 hours — per the requested rule). A separator sits at the top edge of its day block (array position right after the day's oldest message). A pinned chip (the same pill, `IgnorePointer`, flush under the app bar at 64 px — or 6 px when the connection panel / sync banner occupies the top) mirrors the topmost visible row's day: computed by walking the list sliver's laid-out children (`RenderSliverMultiBoxAdaptor` → `SliverMultiBoxAdaptorParentData.layoutOffset` vs the visible range) and refreshed through a coalesced post-frame callback (scroll notifications can arrive mid-layout; notifying synchronously would trip "build scheduled during frame"), fail-open on any render surprise. Hidden while an inline separator itself tops the view (no double label) and for today's rows; the load-more trigger keys on the MESSAGE index so interleaved separators cannot shift the 15th-message threshold.
- Chat screens use `PopScope` to warn before leaving while a transfer is in flight; theme-aware dialogs (`ChatPalette` via the caller's context).
- `analysis_options.yaml` excludes `build/**` and `android/**` from analysis.
