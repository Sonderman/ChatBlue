# Project Overview: ChatBlue

## Project Description
ChatBlue is a Flutter-based peer-to-peer chat application supporting **two transports**: Bluetooth Classic (RFCOMM) and Wi‑Fi Direct (P2P over framed TCP sockets). Both transports are implemented natively in Kotlin and exposed via Platform Channels. State management is powered by GetX; chat sessions and messages are persisted locally with Hive (CE), including image message transfer with progress tracking. The UI follows a modern navy/cyan design language with full light/dark theming.

## Architecture
- **Framework**: Flutter
- **State Management**: GetX (controllers + reactive state)
- **Local Storage**: Hive (CE) with codegen (`hive_ce_generator`) — chat sessions + theme mode (`settings` box)

- **Wi‑Fi Direct (P2P)**: Custom Android native implementation via Platform Channels

  - `BluetoothScanScreen` — BT discovery/paired devices/server mode/connect
  - `WifiDirectScanScreen` — WFD discovery/server (group) mode/connect
  - `BChatScreen` / `WChatScreen` — per-transport conversation UI built from the shared `chat_ui` kit (ChatAppBar, ChatMessageList, ChatMessageBubble, ChatInputBar, ChatSyncBanner, Connect bar, image preview)
- **UI Kit**: `lib/screens/chat_ui/chat_ui.dart` — shared modern chat widgets (navy/cyan, gradient bubbles, glass surfaces, theme-aware `ChatPalette`)

## Notable Implementation Details
- Android Bluetooth Classic (`BluetoothClassicManager`): discovery with RSSI, bonded devices, discoverable request, RFCOMM SPP server/client (accept + connect threads), framed byte-stream protocol, string/byte transfer with progress callbacks, known-address persistence via SharedPreferences. The accept loop stays alive after a connection (peers can reconnect to an already-started server; a new peer replaces the current socket with "replaced").
- Android Wi‑Fi Direct (`WifiDirectManager`): peer discovery, group creation/removal (GO negotiation), client connection via WifiP2pInfo, TCP server/client socket threads with the same framed protocol and progress events; server thread also keeps accepting (same reconnect semantics); permission feature checks.
- Framed protocol: message frames carry a type flag ('text' vs 'bytes') and a 4-byte length; both managers emit `onTransferProgress(direction, current, total, kind)` and `onSocketData(bytes, text, kind)` on separate reader threads; writes run on a single-thread executor (atomic frames, FIFO order).
- `HiveService` persists sessions in the `chat_sessions` box; sessions keyed by id, sorted by `updatedAt`; `MessageModel` stores `imagePath` (not in-memory bytes) plus optional transfer state fields.
- **History sync** (`ChatScreenControllerBase`, SHA-256 based): on (re)connection each side sends a tiny **manifest** — digests of its last 10 messages (text: `sha256(text)`, images/voice: `sha256(file bytes)` + occurrence count). The peer compares against its local set and **requests only what it actually misses**; requested messages travel as `message` packets, each media file in its own packet (base64, ≤ 3 MB). When both sides match, no payload is transferred at all. Dedup uses (text + direction + ±10 s) with the SHA content-hash as fallback. Sync runs once per chat screen, outside the user send queue; a thin "Syncing history…" banner shows frame progress.
- **Send queue**: user text/image sends are serialized in a FIFO queue — an in-flight image transfer never interleaves with other sends; bubbles appear immediately, writes are ordered.
- Image messages: outgoing images are compressed pre-send; both directions use progress bubbles that finalize to image bubbles once transfer completes; incoming bytes saved under application documents directory (background isolate).
- Chat UX: connection status in the header (glowing dot), composer hidden when disconnected and replaced by a **Connect** button that reconnects to the session's device (`connectToPeer`); clearing conversation and full-screen image preview with save-to-gallery (Android 13+ `Permission.photos`/READ_MEDIA_IMAGES, older `Permission.storage`; iOS `photosAddOnly`/`photos`).
- **Voice messages**: tap-to-record (mic button in the composer, runtime `RECORD_AUDIO`), live "Recording 0:12 · Cancel" banner, automatic cut-off & send at 120 s. Files are AAC-LC (.m4a) written to app documents; a short announcement frame (`@@CHATBLUE_AUDIO@@{"duration":…}`) precedes the bytes; transfers reuse the image byte channel (progress bubbles). Voice bubbles offer play/pause, a draggable seek slider and ±10 s jumps (single `just_audio` player); messages persist as `transferKind: 'audio'` + file path (no new Hive fields) and sync as `type: "audio"` packets.
- Dialog/snackbar hygiene: loading dialogs are closed via the root navigator (GetX snackbars are overlay entries, not routes), never via `Get.back()` while a snackbar is open; socket errors are logged only (no snackbar spam); scan errors still surface.
- Progress bubbles are tracked by message id (bubble UUID); Hive writes are debounced (250 ms) and flushed on close; outgoing images are compressed exactly once.
- Chat screens use `PopScope` to warn before leaving while a transfer is in flight; theme-aware dialogs (`ChatPalette` via `Get.context`).
- `analysis_options.yaml` excludes `build/**` and `android/**` from analysis.

## Recent Changes (This Branch)
- **Existing-session messages actually load (missing branch fix)**: with stable identity keys the session was FOUND on direct key hit, but the code had no branch for `session.id == key` — the empty shell stayed and every connect to an existing session looked like a brand-new empty chat with the old history "gone". The direct-hit branch now loads the stored session + messages, and the open logs `Session load: key=… -> … (direct hit|merged|MISS)`.
- **Session re-keying on merge + open diagnostics**: the merge search could only ADOPT a matched session transiently — the next open had to re-run the search (and skipped sessions missed on key variance kept duplicating). Adoption now RE-KEYS the matched session under the computed key (save under the new id + delete the old, `id` is final so the session is re-created) — future opens hit the exact key. Session opens log `Chat open: key=… (peerId=…, mac=…)` in debug, and `DeviceIdService` logs when Hive is unavailable (per-process id would make the peer key sessions differently after restarts).
- **Persistence hardening (sessions vanishing with a message sent)**: the debounced save and the on-close flush both ran WITHOUT error handling — a failing `box.put` disappeared silently and the session never landed (the home list refresh also ran BEFORE the pending flush landed). Now: save/flush failures are logged (`debugPrint`), the home list refreshes only after the flush completes, and adopted sessions are re-persisted at open (fresh `updatedAt`, canonical entry).
- **New sessions persist immediately**: a fresh session was only written to Hive on a dirty event (message, rename, sync) — a chat opened and closed without any of those (J7-initiator round: no messages, early name frame made the rename a no-op) vanished on restart on BOTH sides. `ChatScreenControllerBase.onInit` now calls `_scheduleSave()` for brand-new sessions, so they exist in Hive from the moment the chat opens.
- **Session merge on open + accept-side identity wipe fix**: two bugs kept producing duplicate sessions. (1) `_showIncomingRequest.onAccept` REPLACED `connectedDevice` with the socket map (`_pendingRemote`) — wiping the peer uid the identity frame had just set, so the accepting side never keyed on it; it now MERGES (uid/name preserved, MAC from the frame preferred). (2) When the computed session key misses, the chat now searches existing sessions for the peer — by stored device address first, then by the peer's reported model name (`_findExistingSessionForPeer`) — and adopts the match instead of creating a new one. This also absorbs sessions created by the earlier keying schemes (uuid/`'unknown'`/rotating MACs) without migration.
- **Stable per-install device identity (session merging)**: P2P MACs are randomized and rotate across P2P restarts, and the accepting vs initiating sides keyed sessions differently (uuid vs MAC vs the 'unknown'/dummy placeholders) — the same peer kept spawning new sessions. Each install now generates a persistent device uuid (`DeviceIdService`, stored in the `settings` Hive box) and shares it in the identity frame (`@@CHATBLUE_ID@@<uid>|<mac>|<name>`); the peer uses the uid as the session key (`ChatTransport.connectedDeviceId` → `WdPeerInfo.peerId`), so the same phone always merges into one session regardless of who initiated or whether the MAC rotated. The MAC remains in `device['address']` for display and reconnects; BT keeps its existing MAC-keyed behavior (`connectedDeviceId => null`).
- **No junk session keys from placeholder identities**: on the accepting side (seen on the J7), the socket/group provided only the placeholder 'unknown' or the unresolved dummy P2P MAC (02:00:00:00:00:00), which became session keys and produced "unknown"/duplicate entries in the menu. Now: (1) the session key falls back to a fresh uuid when the device address is a placeholder (`ChatScreenControllerBase.onInit` guard — BT MACs pass unchanged); (2) both sides never SEND or APPLY the dummy (`_isUsableMac` guard in `WifiController`, native `thisDeviceAddress` capture ignores the dummy broadcast); (3) the peer's identity frame still supplies the real name/MAC right after connect, so the session displays correctly.
- **Session identity over the wire (peer MAC in the identity frame)**: the accepting side still got "unknown" in the session list — with no MAC from the socket, `WdPeerInfo`'s fallback literal `'unknown'` became the session KEY and NAME. The `requestGroupInfo` client list proved unreliable for this too. Now each side sends its own P2P MAC (captured from `WIFI_P2P_THIS_DEVICE_CHANGED`, exposed via a new `getThisDeviceAddress` channel method) together with its name in a new `@@CHATBLUE_ID@@<mac>|<name>` frame (`_applyPeerIdentity`); the receiver keys the session on the real MAC and gets the name immediately. The old name-only frame stays as a fallback. Additionally, `ChatScreenControllerBase.onClose` now refreshes the home session list (`HomeController.refreshSessions`) so renamed/new sessions appear in the menu right after a chat.
- **Accepting side now learns the peer's MAC**: the receiver's socket map had no device address, so its chat session fell back to a random UUID key and an "unknown" entry in the session list (the initiator keys sessions by the peer MAC from the scan list). The GO side now also takes the client's `deviceAddress` from `requestGroupInfo` (addresses are core to group membership and reliably populated, unlike names) and puts it in the connected map — the accepting side keys its session on the same peer MAC and shows the real name via the identity frame.
- **Scan list cleared on connection**: once a session begins (READY frame on the initiator, Accept on the receiving side), the Wi‑Fi scan peer list is cleared — the scan screen starts fresh after the chat closes instead of showing the stale pre-connection peers.
- **No premature "Could not connect!" on slow negotiation**: the initiator's 10 s connect timeout hard-failed whenever the socket wasn't up yet — a misleading popup appeared while the peer's request card was still open and the native retry (≈5 s) or slow OEM negotiation hadn't finished; the chat then opened anyway seconds later. The timeout now distinguishes "no signal yet" from "failed": without a socket error or disconnect the attempt holds in awaiting-acceptance (`_pendingAccept`) for a second 10 s window, so the popup only appears on a genuine failure and a late READY frame still opens the chat.
- **Stale "scanning" state on the accepting side**: the acceptor's discovery kept running (and its Dart `isScanning` flag stayed true) through the connection, so after the chat closed the scan screen showed the Start Discovery button as active while nothing was running. The native side now stops peer discovery as soon as the group forms (`CONNECTION_CHANGED` connected branch) and the accepting-side socket handler clears the Dart flag + stops native discovery before showing the request banner.
- **Single "connection lost" notification per disconnect**: a teardown triggered up to three `onSocketDisconnected` events (TCP EOF, the `CONNECTION_CHANGED` disconnected broadcast branch, and `disconnect()`'s own `cancel`) — each surfaced a separate "connection lost" snackbar on the peer (3 duplicates seen when A hung up on B). `WifiDirectManager` now guarantees at most one notification per connection episode (`disconnectNotified` CAS flag, reset in `manageConnectedSocket` for the next episode).
- **WFD reconnects now work end-to-end**: verified on device — the second connection attempt succeeds after a chat closes (stale-channel re-init + `retriedOnce` reset + 5 s retry + group cleanup bundle).
- **Request banner shows the peer's real name (live update)**: WFD sockets carry no peer name pre-accept (`requestGroupInfo` returns an empty client name on several builds), so the receiving side's "Connection request" card showed "unknown". The initiator now sends its `@@CHATBLUE_NAME@@` frame as soon as the socket is up — BEFORE the READY handshake — and the banner title is a live `Rxn<String>` (`ConnectionRequestBanner` gained an optional `liveName` observable): the card flips from the localized unknown placeholder to the real device name the moment the frame lands, without waiting for accept. The accepting side also sends its name early (idempotent with the existing post-accept send).
- **Connection banner shows the peer's real name**: the receiving side's "Connection request" card used to show "unknown" — the socket carries only an IP, no P2P name. The GO side now queries `requestGroupInfo` when a client connects (1 s fallback so the handshake never stalls) and includes the client's device name in the connected map (`WifiDirectManager.handleAcceptedSocket` + `peerName` param).
- **WFD "connects once, then never again" — stale channel + stale flag fix**: (1) after a group teardown the P2P service restarts on most devices; a channel obtained before the restart turns STALE and every op on it fails instantly — `WifiDirectManager` now tracks the restart (`channelDirty` on `WIFI_P2P_STATE_DISABLED`), re-initializes on the next ENABLED broadcast and defensively inside `connect()`. (2) The `p2pEnabled` hard-fail in `connect()` was REMOVED: the flag only updates on explicit state broadcasts and goes stale when the framework silently re-enables P2P (discovery works, connect still rejected with "Wi‑Fi Direct is disabled"). (3) Connect retry backoff raised 1.5 s → 5 s (`RETRY_DELAY_MS`) so a retry issued during the P2P service restart settles in time.
- **Detailed connect errors surfaced**: the scan screen now shows the actual native failure reason ("Wi‑Fi Direct is disabled", "Location is turned off", "connect failed: BUSY (2)", …) instead of the generic "Could not connect!" — `WifiController.lastConnectError` captures the detail from the connect attempt's socket-error handler and `WifiDirectScanScreen` uses it in the failure snackbar.
- **Reconnect fix (chat controller leak)**: chat controllers are registered via `Get.put` and GetX never auto-deletes them on route pop, so `ChatScreenControllerBase.onClose()` — the socket disconnect, P2P group teardown and `_chatOpen` reset — never ran. The first connection stayed alive and every later attempt failed ("connects once, then never again"). Both chat screens now `Get.delete<…>()` their controller in `State.dispose()`, which runs `onClose` reliably and gives the next session a clean connection + chat state.
- **Auto Wi‑Fi enable on the WFD scan screen**: when the device's Wi‑Fi radio is off, the scan screen now shows a "Turn on Wi‑Fi" state (localized) instead of the scan controls — the button opens the system Wi‑Fi settings panel (popup panel `Settings.Panel.ACTION_WIFI` on Android 10+, settings screen below; apps can't silently enable Wi‑Fi since Android 10), then polls `isWifiEnabled` every 500 ms (≤15 s) and automatically flips back to the normal controls once the radio is on. New channel methods `isWifiEnabled` / `requestEnableWifi` (native `WifiDirectManager` + `MainActivity`), wired through `WdPlatformChannel`/`WifiDirectService` into `WifiController` (`isWifiOn`, `enableWifi`, `_refreshWifiState`; `startDiscovery` re-checks and bails to the enable state while off).
- **WFD reconnect fix (lingering group)**: after a chat closes, the P2P group stayed alive at the system level — the next connect attempt failed with BUSY on OEM builds ("works once, then can't reconnect", seen on the J7). `WifiDirectManager.disconnect()` now removes the group after ordinary client-mode sessions (a new `groupOwnerMode` flag preserves the group + accept loop for explicit Start Server mode, keeping the documented reconnect-to-started-server behavior); `connect()` now WAITS for the group removal to complete before starting negotiation instead of fire-and-forget + 600 ms, which was too short for Samsung's group teardown.
- **Peer device names in WFD chat app bar**: Wi‑Fi Direct sockets carry no peer name/address in the native connected map, so chat app bars fell back to an opaque placeholder. Now: (1) the tapped scan entry's name/address is patched into the connection identity at READY (`WifiController.connectToDevice` caches it, `_dispatchSocketData` merges it — this also fixes the lost device address that broke reconnect-from-home); (2) both sides exchange their real device names via a new `@@CHATBLUE_NAME@@<model>` frame sent right after the handshake (`_sendOwnName`/`_applyPeerName`, device model via `device_info_plus`), updating the connection identity and the persisted session name; (3) `ChatAppBar` title became reactive (`Obx` over `transport.connectedDeviceName ?? peerName ?? chatSession.name` via a new `RxString peerName` + `updateSessionName()` on `ChatScreenControllerBase`) so the bar updates when the name frame lands instead of showing the initial fallback until the next rebuild.
- **Chat open crash fix (LateInitializationError)**: `ChatScreenControllerBase.onInit` assigned `late chatSession` only AFTER the `await loadChatSession(key)` — the first frame (`ChatAppBar` reads `chatSession.name`) built while onInit was suspended, throwing `LateInitializationError` on every chat opened through the scan/connect flow (no `Get.arguments`). The session is now created synchronously before the first await and the Hive lookup hydrates an existing session (messages included) in place afterwards. Fixes both transports (BT had the same latent crash on scan-flow chat opens).
- **Settings opened as a pushed route**: Bluetooth / Wi‑Fi remain in-place `IndexedStack` tabs, but the Settings entry (app-bar icon) pushes `SettingsScreen` as its own route with back navigation. Its Scaffold/AppBar (added for the earlier theme fix) keeps it rendering correctly as a route.
- **In-place tabs instead of pushes**: Bluetooth / Wi‑Fi / Settings are real `IndexedStack` tabs now — the bottom bar either switches content or (Settings, tab 3, opened from the app bar icon) flips the stack index; no route is pushed anymore. The home app bar shows only on the Chats tab (scan screens and Settings render their own app bars).
- **Settings theme breakage fix**: `SettingsScreen` had no Scaffold of its own — it relied on the host's body when it was a bottom tab, so opening it as a pushed route rendered unthemed (wrong background/text colors). It now owns a `Scaffold` + `AppBar` and renders correctly in any host.
- **Home navigation reshuffle**: Bluetooth and Wi‑Fi Direct entry points moved from the app bar into the bottom navigation bar (second and third destinations, pushing their scan screens); Settings moved the other way — a single app-bar icon now opens `SettingsScreen` (the old Settings bottom tab is gone). App bar title is always the app name; tooltip-only entries `scanBluetoothTooltip`/`scanWifiTooltip` replaced by `bluetoothTab`/`wifiTab` labels.
- **Self-initiated popup race fix (first-try scenario)**: the "Connection request" card appearing on the side that just initiated a connect (seen on the very first attempt, when both devices are typically acting at once) is a simultaneous-two-way-connect race: the peer's back-connection can arrive before/after `connectToPeer`'s guard flags flip. Both controllers now record `_connectInitiatedAt` and treat **every socket event within 20 s of an initiation as part of that initiation** (`_outgoingConnect || _pendingAccept || withinInitiationWindow`), so a card can never appear for a link we started; the window clears on READY/disconnect.
- **False "Could not connect!" fix**: when the peer hadn't answered yet (its request popup still up), a connect timeout reported "Could not connect!" even though the link was alive and waiting. `ChatTransport` gained `isAwaitingAcceptance` (backed by `_pendingAccept` in both controllers); scan screens and the chat reconnect button now show a neutral "Waiting for acceptance" snackbar in that state and only report failure when the socket actually died — the READY frame still opens the chat when the peer accepts late.
- **Message deletion + id persistence fix**: users can now delete their own messages — long-press a text bubble opens its selection toolbar with **Copy** (whole message when nothing selected) plus **Delete** for own messages; image/voice/progress bubbles get a themed confirm dialog on long-press (own messages only, transfers in flight excluded); `ChatScreenControllerBase.deleteMessage(id)` removes from UI + Hive. Root cause of "deletion does nothing": `MessageModelAdapter` never wrote `id` to Hive (generator skipped it — no `@HiveField`), so restored sessions had all-null ids and `deleteMessage` bailed. The model is now `@HiveField`-annotated and the regenerated adapter appends `id` at index 9 (backward compatible: old records read `null`); chat open backfills ids on legacy messages and persists them. `flutter analyze lib` → 0.
- **Initiator "Connection request" popup fix**: the side that initiated a connect could still get a request card for its own link. `connectToPeer`'s 10 s timeout branch cleared `_pendingAccept` while the socket was often still alive (peer accepting late, or a second connection event for the same link) — the next `onSocketConnected` then fell into `_showIncomingRequest`. The flag is now released only by the READY frame, an actual socket disconnect or a socket error, so the initiator never sees its own request popup (and accepting it can no longer open the peer's chat).
- **Sync banner position fix**: `ChatSyncBanner` hung ~status-bar-height below the app bar because its top margin re-added `MediaQuery.padding.top` inside a `SafeArea` that already consumed it (double counting). Banner now sits flush at 66 px (toolbar 64 + 2 gap); `ChatMessageList` head inset fixed the same way (72 px) — no `padding.top + …` offsets remain inside the SafeArea body.
- **READY frame leak fix**: the `@@CHATBLUE_CONNECT@@` handshake frame could surface as a regular chat bubble on the initiating side. `_pendingAccept` is reset by the 10 s connect timeout / disconnect handler; a READY frame arriving afterwards (peer accepted late) fell through to the chat consumer. Both controllers now match the frame **unconditionally** in `_dispatchSocketData` (and use `connectedDevice ??=`, so an already-bound device is preserved) — the frame binds the connection and can never be rendered as a message.
- **trParams placeholder fix**: GetX 4.7.x's `trParams` only replaces `@param` placeholders (never `{param}`) — all localized strings with parameters (`nearbyDevices`, `pairedDevices`, `deleteChatTitle`, `versionLabel`, `connectErrorDetail`, `recordingLabel`, `imageCaption`) switched from `{...}` to `@...` syntax; previously the raw `{count}` text was rendered on screen.
- **Scan screen TR layout fixes**: Turkish button labels overflowed the two-button row on narrow screens ('Keşfedilebilirliği Durdur' + 'Taramayı Durdur' > 360dp) — buttons now sit in `Expanded` + `FittedBox(scaleDown)` rows on both scan screens; TR labels shortened ('Görünür Yap' / 'Görünürlüğü Kapat'). Bluetooth scan error strings moved from hardcoded Kotlin literals to `res/values/strings.xml` + `values-tr/strings.xml` (`bt_scan_error_*`), so the snackbar body follows the device language too.
